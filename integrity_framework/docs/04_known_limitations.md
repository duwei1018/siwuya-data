# 04 · 框架的盲区 · Known Limitations

> 这一文与 [METHODOLOGY.md §7](../METHODOLOGY.md#7-known-limitations--已知盲区) 互补,用更长的篇幅诚实展开。**写一份只列优点的方法论是 marketing,这是方法论。**

---

## A 类 · 算法层面的盲区

### A1. 单一指标 → 有损压缩

把"诚信"压缩到 0-100,本质上有损。
- 一个分 80 的公司,可能是"100 条 verdict 平均"也可能是"5 条 verdict 平均",信息量天差地别。
- 一个分 80 的公司,可能是"很多 partial"也可能是"少量 broken",意义完全不同。

**应对**:任何使用本框架分数的人,**必须**同时给出 `breakdown` 与 `counted_verdicts`。把分数当作入口,而不是结论。

### A2. 时间衰减是直觉,不是实证

`DECAY_YEARS = 3` 没有 backtest 支撑,是基于"管理层任期"+"战略 cycle"的推理。在 v0.2.0 之前不会有数据可以支撑。

**应对**:不要把分数当成跨长时间窗口可比的工具。

### A3. 不区分 outcome 严重程度(除特殊 tag 外)

一个 broken = -15 是固定的,不管是"承诺增长 25% 实际 22%" 还是"承诺增长 25% 实际 -10%"。

**应对**:reasoning 必须写实际差距,使用者下钻到 breakdown 看具体数字。

### A4. 不奖励兑现 → 区分度问题

"承诺多 + 兑现多" 与 "承诺少 + 兑现少" 都是 100 分。

**应对**:这是设计选择(见 docs/02),不是 bug。如果你需要"沟通质量"维度,可以单独 build,不要混进诚信分。

### A5. severity_tag 白名单很窄

只有 3 个:`financial_misconduct / audit_qualification / fraud_admission`。

很多真实情况不在内(比如关联交易披露不充分、信息披露延迟、内幕交易)。

**应对**:不在白名单里的严重性,**不**算入分数,但 reasoning 必须详细记录,留作未来扩展依据。

## B 类 · 数据层面的盲区

### B1. 承诺识别的语义模糊

MVP `promise_extractor` 是关键词匹配,会:
- 漏掉:用了非典型措辞的承诺("我们瞄准...""有信心达到...")
- 误报:口语化用 "will" 但不是承诺的句子("we will see how the market reacts")

**应对**:框架本身不在生产里跑 promise_extractor。所有 promise 都应该是**人工编写后入库**,extractor 只用作提示工具(给个起草版让人审)。

### B2. 跨文化与跨市场差异

中国 A 股、港股、美股的"指引文化"完全不同:
- 美国:有强 SOX/Reg FD 约束,自愿性指引一旦给出就有法律含义
- 港股:介于两者之间,机构指引被认真对待
- A 股:多数是"业绩预告"形式,自愿性指引相对少

同一种"未达预期"在三地的合规含义不同。本框架**当前不区分**。

**应对**:跨市场比较公司诚信分**没有意义**;只在同市场内比较。

### B3. 承诺时点的"语境偏差"

> "我们对未来充满信心" 在 2020 年说与在 2008 年说,意义不同。

框架不记录宏观语境,所有 promise 都是"独立时点的承诺"。

**应对**:reasoning 鼓励写宏观背景,但分数本身不带这个信息。

### B4. 维护者的标注偏差

任何 verdict 都来自某个研究者的判断。研究者本身有:
- 行业偏好(熟悉的行业判得严,不熟的行业判得松)
- 时间偏好(刚发生的判得严,远的判得宽容)
- 人际偏好(尤其在小行业,认识管理层的可能性高)

**应对**:`judged_by` 公开,允许任何人 audit 某个研究者的所有 verdict 寻找系统偏差。鼓励多人覆盖同一公司形成 cross-check。

### B5. 沉默的承诺

> 公司从来不给 guidance。

这种公司框架**不**评估(没 promise = 没 verdict = 没分)。

**应对**:框架不评估 ≠ 公司不可信任。这只是说"本框架不适用",不要 inferred。

## C 类 · 法律层面的边界

### C1. 不是信用评级

明确不替代 S&P / Moody's / Fitch / 中诚信 / 大公等监管批准的评级机构。任何监管/合规场景请使用监管批准的评级。

### C2. 不构成投资建议

任何使用本分数做投资决策的人对自己的决策负全责。详见 [DISCLAIMER](../../DISCLAIMER.md)。

### C3. 第三方权利

公司名称 / 标识 / 文件 / 数据的版权归原所有者。本仓库引用是基于公开信息的研究目的。任何第三方主张权利的内容,会按合理流程处理(走 issue,不会假装看不见)。

### C4. 个人姓名

`made_by` 字段会写入具体管理层个人姓名。这是公开人物的公开发言,属于研究合理引用。如某管理层主张本仓库内容侵权,走 issue,我们会评估并必要时处理。

## D 类 · 治理层面的盲区

### D1. Maintainer 集中度

当前 maintainer 是 @siwuya 一人。任何方法论修改都通过他。

**风险**:单点失败 / 单一视角偏差。

**计划**:Stage 6+ 之后随社区积累引入更多 maintainer。

### D2. PR 审核可能过松

社区贡献的 verdict 在 PR 阶段被 maintainer review,但人工 review 必然有过松的风险。

**应对**:GitHub Actions 跑 schema 校验是硬门槛;`judged_by` 公开是软监督——任何低质量 verdict 都能被 trace 到具体署名,形成自我纠错机制。

---

## 总结:何时本框架有用,何时没用

**有用**:
- 同市场内比较已建立 verdict 池的公司
- 用作研究入口,下钻到 breakdown 形成 thesis
- 公开的、署名的、可挑战的研究判断 audit trail

**没用**:
- 跨市场比较
- `counted_verdicts < 5` 的公司
- 任何未署名 / 未带 reasoning 的 verdict
- 把分数当结论而不是入口
